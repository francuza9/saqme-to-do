# Sync protocol and conflict rules

Single user, several devices (desktop PCs, phones). The Worker is the meeting point and keeps the
canonical state; every device works locally first and exchanges changes in the background. A list can also
be shared with other people, who sync that one list from the owner's Worker ([Shared lists](#shared-lists)).

## Data model

Every syncable row has **fields**, each with a value and a timestamp (`ts`, milliseconds, see
[Clocks](#clocks)), plus the server's change sequence `seq`:

| Kind | Id | Fields |
|---|---|---|
| `task` | 8–32 chars `[0-9a-z]` (the `^id` in markdown) | `place` = `{ project, parent, pos }`, `text`, `status`, `due` = `{ date: 'YYYY-MM-DD', time: 'H:MM' or '' }` or `null`, `notes`, `deleted` |
| `project` | same format | `name`, `pos`, `deleted` |
| `setting` | `notifyAt`, `tz` | `value` |
| `conflict` | generated by the server | `resolved` (plus read-only `task`, `field`, `value`, `other`, `at`, `device`) |

- `place` is one field on purpose: project, parent and position move together, so a move is atomic.
- `pos` is a **fractional order key** (`a0`, `a0V`, `a1`, …; compared as plain ordinal strings) from
  David Greenspan's fractional indexing. A move only re-keys the moved task; siblings sort by `(pos, id)`.
- Tasks are never removed from the database: `deleted = true` is a tombstone (restorable).
- Statuses: `' '` to do, `/` in progress, `x` done, `>` postponed, `!` blocked, `-` failed, `~` abandoned.

## `POST /api/sync`

```jsonc
// request
{
  "deviceId": "pc-1a2b3c4d5e",          // stable per device
  "cursor": 1234,                        // last seq this device has seen (0 = everything)
  "changes": [                           // at most 100 per request
    { "kind": "task", "id": "k3j9x2ab", "fields": {
        "text":   { "v": "Call the plumber", "ts": 1790000000000, "base": 1789999000000 },
        "status": { "v": "/",                "ts": 1790000000000, "base": 1789999000000 } } }
  ]
}
// response
{
  "cursor": 1240, "more": false,         // more = call again with the new cursor
  "changes": [ { "kind": "task", "id": "k3j9x2ab", "seq": 1240, "fields": { "text": { "v": "...", "ts": ... }, ... } } ],
  "rejected": [ { "kind": "task", "id": "...", "field": "place", "reason": "move would create a cycle" } ],
  "serverTime": 1790000000123, "dbId": "9f2c4e1a0b7d3c55"
}
```

- `base` = the `ts` of the version the device edited (`-1` for something new). It is how the server tells
  a sequential edit from a concurrent one.
- The response contains **every row changed since `cursor`**, including the rows this request touched,
  in their canonical (merged) form. Pages hold at most 600 rows per table; `more` asks for another call.
- `dbId` identifies the database. If it changes (database recreated, or pairing with a different account),
  devices push their whole state again; the server merges it in.

## Merge rules

For each incoming field (`cur` = what the server has, `inc` = the change):

1. **Nothing there yet** → take it.
2. **Same device wrote `cur`** (the server remembers the last writer per field) → plain last-writer-wins,
   never a conflict with yourself (covers resends after a lost response).
3. **`inc.base == cur.ts`** → the device edited exactly the current version: take it (even if its clock
   lags; the stored `ts` is bumped past `cur.ts`).
4. Otherwise the edits were **concurrent**:
   - same value → no conflict;
   - different → **newest `ts` wins** (exact ties: the larger value, deterministically). For `text`,
     `status`, `due` and `notes` the losing value is stored in `conflicts` with the winner for reference.

Different tasks, and different fields of one task, never conflict.

**Edit vs delete — the newer action wins:**

- A delete older than the newest edit made by *another* device is ignored, and recorded as a `deleted`
  conflict ("deleted on one device, edited on another") so it can still be confirmed.
- An edit newer than a delete brings the task back (`deleted = false`), also recorded as a conflict.
- An edit older than the delete is stored (the content stays current) but the task stays deleted.
- The same applies one level up: acting on a task after its project was deleted restores the project.

**Moves** are refused if the new parent is the task itself or one of its descendants (the server walks the
ancestor chain in the same transaction); the device gets the canonical row back. A task whose parent is
deleted, unknown or in another project is shown under its nearest live ancestor, or at the top level.

**Projects:** renames and deletes sync like task fields (last-writer-wins). Deleting a project does not
delete its tasks; they stay with the deleted project (shown under *Recently deleted*) and come back with it.

**Conflicts** reach every device as `conflict` rows. Resolving one sends `resolved: true`, plus — when the
other version is chosen — an ordinary edit of that field, so all devices converge.

## Server-side safety

- A request is validated and normalized (ids, statuses, dates, time format `H:MM`, text without line
  breaks, notes without trailing spaces, size limits). Invalid changes are reported in `rejected`.
- Timestamps in the future are clamped to the server's clock.
- **Optimistic concurrency without transactions:** the server reads the current `seq` and all affected rows
  in one D1 batch (a consistent snapshot), merges in JS, then writes everything in one batch that starts by
  re-inserting the fixed `meta.lock` row *if `seq` moved in between*. That violates the primary key, D1 rolls
  the whole batch back, and the request retries with fresh data. A batch is applied completely or not at all.
- Each written row gets the new `seq`; cursors are just "give me everything with `seq > n`".

## Clocks

Devices stamp edits with `Date.now()` corrected by the offset to the server's clock (estimated from each
response's `serverTime`), strictly increasing per device. The desktop stamps a change with the **time the
list file was saved**, not the time the sync loop noticed it, so "newest wins" stays fair.

## Desktop engine (PowerShell, and its JavaScript port)

The Windows app runs it in PowerShell (`desktop/sync-core.ps1`); the Linux/macOS app runs a line-by-line
port in JavaScript (`local/engine.mjs`) with the same state file format, rules and plans. What follows applies
to both.

State in `sync\state.json`:

- **R** — server rows as last received.
- **S** — the *base*: what the files reflected at the last reconcile, plus local changes already queued.
- **Outbox** — local changes not yet acknowledged. Persisted *before* sending; after a crash the same
  changes (same timestamps) are sent again, which the merge rules make harmless.
- **Planned** — for half an hour after a plan (step 4) rewrote lists: what they held before, per task
  field the plan changed and per task it brought into a list (see "Saves from an older copy").
- **Missing** — when each list that vanished was first seen missing; **Guard** — the deletes held back.
- **Notices** — what a shared list's server did not take; **Shared** — which of one's own lists are shared
  (see [Shared lists](#shared-lists)). A shared list's engine keeps its state in `sync/shares/<id>.json`.

One cycle:

1. Read all lists. A list is used only if it could be read, was not written in the last 1.5 s, holds no
   NUL characters (what a power cut can leave behind), and every task has a unique id. Lines without an id
   get one first (in a separate tiny write; ids that an editor dropped are matched back by text), and
   nothing is sent for that list in that cycle. A file that is not valid UTF-8 is read in the legacy code
   page (Windows: the system's; Linux, macOS: Windows-1252) and written back as UTF-8.
2. **Diff** parsed lists against S → field changes (text, status, deadline, notes, parent/position from the
   indentation and line order, deletes for lines that vanished). Positions: the longest run of siblings
   whose base keys are still in increasing order keeps its keys; only moved lines get new ones.
   A list moved to `lists/.trash` (how the apps delete one) deletes its project. A list that is simply
   gone (moved out and back, a sync client re-downloading the folder, `git checkout`) decides nothing until
   it has been gone for two cycles and 10 seconds. Deletes are never decided while any list was unusable
   (the line may just have moved there), and are **held back** when a large share vanishes at once: 5+
   tasks and more than half of one list (a gone list counts with all its tasks), or 25+ tasks and more than
   half of all. Settings → Sync shows it; confirming deletes exactly what was held back, and whatever
   vanished since is weighed again.
3. Fold the changes into S and the outbox, save, send, store the returned rows in R.
4. If every list was usable in step 1 and none changed since, build a **plan** that makes the files match
   R where R differs from S (a cycle that had to leave a list out never plans: that list's newest edits
   are not in S yet):
   in-place line edits, removed lines (subtasks move up a level), moves and new tasks placed among their
   siblings by `pos` (after the previous sibling's subtree, so a task stays in its heading's section),
   new/renamed/deleted (→ `lists\.trash`, only if the list still holds what the plan saw) list files, tab
   order. Only the fields the server changed are
   written into a line. Moved and arriving tasks are placed parents first, each after the already-placed
   sibling with the next smaller `(pos, id)`. All files are staged first; lists that gain tasks are
   replaced before lists that lose them. Headings, prose and blank lines are kept as they are.
5. The UI thread checks every file still matches, writes them all (temp + replace), and only then is S set
   to R. It does this only between edits, never while a menu or popup holds a task, and not while a save of
   its own is still failing.

The widget itself saves every edit at once. If the open list changed on disk since it was loaded (an editor
or an AI assistant), the save replays the widget's edits onto the new file content by task id instead of
overwriting it; if the list was renamed meanwhile, it follows the rename. It writes only over exactly the
content it merged with: a list another program holds or changes meanwhile waits, and is merged again. A save
that keeps failing is retried and reported, never silently dropped; quitting or switching lists then leaves a
copy in `lists\.recovery`. A list changed by another program is reloaded once it has not changed for 1.5 s
(it may still be being written), and one that cannot be read when its tab opens shows as busy and is never
written over.

**Tasks leave a list only on purpose.** Before every write the widget checks that each task that was in the
file or in memory is still in the text it is about to write (`Get-UnexplainedLoss` in `sync-core.ps1`). The
only exceptions are an explicit delete, a move to another list, Ctrl+Z, and a task another program deleted
from the file meanwhile. A write that would lose any other task is refused: nothing is written, the list is
shown as it is on disk, and the window says so. Whatever a bug in the app does, it cannot become a delete
that sync sends everywhere. (In 1.0.0 dragging a task removed it, and its subtasks, from the list: the drag
used a live view of the list after removing those items from it. Moves are now shared, tested functions,
`Move-ListBlock` and `Step-ListBlock`, that copy the moved block and change nothing when a drop cannot be
done.)

**Undo and Recently deleted on the desktop.** Ctrl+Z puts back the files of the last change (a move puts back
one list, a move to another list both), as long as nothing else has changed them since. Deleted tasks are
kept for 30 days in `recently-deleted.json` in the data folder, outside the lists folder. With sync on, tasks
deleted on other devices (from the engine's state) show there too. A restore writes the lines back with their
ids, which sync sends as not deleted. A restore of a task that a plan removed tells the engine so, otherwise
the engine would take the line for a save from an older copy (below) and keep the delete.

On first contact with a server (empty state), the desktop pulls first and adopts server projects with the
same name instead of creating duplicates; the phone does the same for lists made before pairing. An empty
lists folder receives the server's lists right away.

**Saves from an older copy.** An editor or an AI assistant may read a list, the app then writes a change
from another device into it, and the editor saves its older copy. For half an hour after a plan, the engine
recognises that for the tasks the plan touched: a field put back to its value from before the plan is sent
as of then (the other device's newer value stays, the older one is kept as a conflict); any other change to
such a field is sent as concurrent with the other device's (newest wins, the other is kept as a conflict);
a task the plan brought in that the save dropped is sent as a delete dated before the task arrived, so the
server keeps it, records the conflict, and the next plan puts it back. Nothing is silently undone.

**A restored server.** When the Worker's database goes back in time (D1 Time Travel or a backup restore),
the server says so (`restored`, or a cursor lower than the device's). The engines then start over as on
first contact: they pull everything and merge the lists in again, so what the restore brought back reaches
the files and what was written since is not skipped. Resending the old base instead would re-apply the
deletes a restore is usually meant to undo.

## Linux and macOS: one folder, two engines

The Linux/macOS app keeps a local copy of the sync server (the Worker's own code on SQLite) for its window,
and runs the desktop engine twice on the same lists folder: once against that local store (device id
`files`), and, when cloud sync is set up, once against your Worker. Each engine sees the other's writes as
ordinary file edits, so the folder is the meeting point:

```
window <-> local store <-> [engine] <-> lists/*.md <-> [engine] <-> your Worker <-> phones, other computers
```

Both engines live in one process and apply their plans synchronously, so they never write a list at the
same moment; each re-checks a file's content before replacing it. Conflicts between this computer and other
devices are recorded by your Worker (visible on the phones); conflicts between the window and the files are
recorded by the local store (visible in the window). The cloud engine also syncs `notifyAt` between the
local store and the Worker.

## Phone engine (JavaScript)

Rows live in memory + IndexedDB. An edit sets the local value immediately and adds `{ v, ts, base }` to the
outbox entry of that row (keeping the first `base` if the field was already pending). After a response:
fields whose outbox `ts` is unchanged are acknowledged and removed; rows from the server replace local
ones, except for fields still pending in the outbox, which stay on top until they are sent.

## Shared lists

Everyone runs their own Worker with their own key; there is no central server. A shared list **lives on its
owner's Worker**. The people it is shared with sync that one list from there, with a key of their own that
reaches nothing else, next to (or without) their own sync.

### The owner's side

The owner shares a list from its tab (right-click or long-press > **Share…**; on Windows also the share icon
that shows on the current tab while the mouse is over it). Sharing needs the owner's own sync, since the
list must be on their Worker; without it the item is there but disabled, and says why.

- **A name for the person** ("Nuca"), only ever shown to the owner, to recognise and revoke them later.
- **Access:** *Can edit* (add, change, check off and delete tasks in this list) or *Can view* (see the list
  and its updates, change nothing).
- An **invite link**, `https://<owner's Worker>/join#code=<code>`: copied, shown, and as a QR code on the
  desktop. The code is 128 random bits after the `#` (never in a server log), works **once**, for **24 hours**,
  until claimed or cancelled.
- The same view lists everyone the list is shared with: name, access (changeable), joined or invited and
  when. **Revoke** ends a person's key at once; **Cancel invite** voids an unclaimed invite. Shared lists show
  a small badge on their tab, for the owner and for the people they are shared with.

Owner routes (owner's key): `POST /api/shares/invite { projectId, alias, access }`, `GET /api/shares?project=`,
`POST /api/shares/update { id, access }`, `POST /api/shares/revoke { id }`. The owner's `/api/sync` responses
add `shared: [project ids]` (lists with a person or an open invite), for the badge.

### The invite and the key

`POST /api/shares/claim { code }` (no key) answers `{ token, projectId, projectName, access, ownerUrl, kind }`
once: it is a single `UPDATE … WHERE invite_code_hash = ? AND revoked_at IS NULL AND invite_expires_at > now
RETURNING …`, so two claims cannot both win, and a wrong code reads one index entry and writes nothing. The D1
table `shares` keeps SHA-256 digests only: of the invite code until it is claimed, of the person's 256-bit key
afterwards. Revoking sets `revoked_at`; every request looks the key up, so it gets `401 { error: 'revoked' }`
from the next request on. `POST /api/shares/leave` (with the person's key) ends their own key, nothing else.

**Moving to another app** ("Move to my Saqme app", for a list used in the browser): `POST /api/shares/transfer`
with the person's key makes a one-time **move code** for the same share (24 hours, the same link format). Claiming
it answers `kind: 'move'` with a new key for that share; the old key's digest moves to `old_token_hash` and it gets
`401 { error: 'transferred' }` from then on, so the browser copy stops syncing and goes. The owner still sees one
person. Migration `0003_remotes.sql`.

### What a shared list's key can do

A request with a share key is scoped to its project, checked against the same D1 snapshot the merge uses
(a task the owner moves out meanwhile cannot slip through):

- `/api/sync` returns only that project, its tasks and their conflicts (with the recording device left out):
  no settings, no other project, no other task. A task the owner moves to another list comes as
  `{ kind: 'task', id, gone: true }` (table `moved_out`), so it leaves the person's copy without them
  learning anything about where it went. The response adds `share: { projectId, access }`.
- With **edit** access, changes to tasks of the list and their conflicts apply as usual. Refused, with the
  list's own rows sent back as they are (so the device's copy reverts) and nothing outside the list ever sent:
  a task outside the list (created, edited, deleted, or moved in), a task moved out, a parent outside the list,
  the list itself (rename, order, delete: "only the owner can change the list itself"), settings, and
  everything once the owner deleted the list.
- With **view** access every change is refused ("this shared list is view-only") and nothing is written.
- Its own **reminders** (for someone using the list in the browser from the owner's address): `GET /api/config`
  and `POST /api/push/subscribe { subscription, tz, notifyAt } | unsubscribe | test` keep push subscriptions of
  that share only (table `share_push`, at most 10), never the owner's. And `/api/shares/transfer` (above).
- Every other route (pairing, sharing, the relay, settings) answers 403; a revoked key gets 401 everywhere.

Covered by `worker/test/workers/shares.test.js`.

### The relay: lists shared with a phone that has its own sync

The phone app may talk to its own origin only (`connect-src 'self'`), so a paired app never calls an owner's
Worker itself: **its own Worker does, server to server** (`worker/src/remotes.js`, table `remotes`), with the
person's own key:

- `POST /api/remotes/join { link }` claims the invite at the owner's and keeps the share key in D1; it answers
  `{ remote: { id, server, projectId, name, access, state }, kind }` (never the key). A second key for a list
  that is already there is given back (`/api/shares/leave`) and the answer is 409; so is an invite to one of its
  own lists. A move code lands on the list the phones already have.
- `POST /api/remotes/<id>/sync` takes a normal sync body and answers with the owner's answer and status;
  `POST /api/remotes/<id>/leave` ends the key there and here. `POST /api/remotes/adopt { server, token, name }`
  takes over a key the app had on its own (joined in the browser before it was paired).
- Every `/api/sync` answer of the person's own Worker lists `remotes`, so their other phones add the list by
  themselves. Leaving on one phone leaves on all of them (one key per person and list).
- When it ends: `401 { error: 'revoked' | 'transferred' | 'left', convert }`. After a revoke the first phone to
  ask gets `convert: true` and keeps the list as one of its own (new ids, as below); the others drop their copy
  and get that one through their own sync. A list the Worker no longer has (404 "no such shared list": set up
  again, or paired with another Worker) is kept as an own list too.
- **Not an open proxy.** Only the person's own key works there (a share key gets 403). It calls three routes,
  `/api/shares/claim`, `/api/sync` and `/api/shares/leave`, on an https origin checked at join: a host name with
  a dot, no IP address (v4 in any notation, v6), no `localhost`, `.local`, `.internal` or `.home.arpa`, the
  default port, no user name or password, nothing after the host. No redirects are followed, it gives up after
  20 s, reads at most 4 MB, wants a JSON object, and sends nothing but the share key (and `x-saqme-relay: 1`).
  The owner's status comes back unchanged (a 404 of the owner's comes back as 502, so it never reads as "no such
  list here").

Desktop apps (Windows, Linux, macOS) are not limited by a browser's policy and talk to owners' Workers directly.
Someone using a list in the browser **from the owner's address** (no Saqme of their own) is on the owner's
origin, so that copy talks to it directly too. Covered by `worker/test/node/relay.test.js`.

### Reminders on phones

- **With a Worker of one's own:** its cron (every 5 minutes) first reads the lists in `remotes` from their
  owners' Workers (the 3 read longest ago, at most 6 requests a run, well within the free plan's 50
  subrequests and 50 D1 queries per run; table `remote_tasks`: id, text, status, deadline), then computes the
  reminders of one's own tasks and those together, in one's own time zone and at one's own summary time, with
  the same dedupe keys. With more than 3 shared lists each is read every few runs, so a deadline set in one
  minutes before it is due may be missed. A task moved out of the list, a list the owner deleted, or one no
  longer shared stops reminding.
- **In the browser from the owner's address** (no Worker): the app subscribes for push with the list's key
  (`share_push`, with the phone's time zone and summary time, sent again when either changes); the owner's
  cron sends that list's reminders to those subscriptions only, with dedupe keys of their own (`s:<share>|…`).
- **Never twice:** once a key is used through the person's own Worker (the relay marks it, `relayed_at`), the
  owner's Worker stops sending that share's browser reminders (for a week after the last use); a move deletes
  them outright, and leaving or a revoke ends them. Two separate invites for one person (one in the browser, one
  in the app) are two shares, and remind twice: use *Move to my Saqme app* instead.
- Desktop apps remind from the files, as for one's own lists.

Covered by `worker/test/node/shared-reminders.test.js`.

### The person's side

Every client keeps one **session per list**: its own sync (if any) and one per shared list, each with its own
cursor, `dbId`, clock offset and restore handling. Rows from a shared list's server land only if they belong
to that list (its project, its tasks, their conflicts); this device's own server can never overwrite them, and
nothing of a shared list is ever stored in one's own lists (on the phone, its key is kept by one's own Worker's
relay, in a table of its own, never in the synced rows).

- **Phone app** (`store.js`): `meta.shares` holds the bindings in IndexedDB. Paired: `{ via: 'relay', remote,
  server, access, projectId, pos, cursor, dbId, … }`, synced through the relay above (no key on the phone).
  Not paired, used from the owner's address: `{ via: 'direct', token, … }`, synced with that origin directly;
  when such an app gets paired, the key goes to its own Worker (`/api/remotes/adopt`). Unpairing keeps relayed
  lists and what was typed into them; they wait (the tab says so) and go on when the app is paired again. A
  shared tab's place is kept on the device only, and a list whose name another list here has shows whose it is:
  "Groceries (from nuca)" (`pairing.js serverLabel`: the account part of a workers.dev address, else the host).
  A view-only list is read-only in the app (and the store refuses changes to it); moving a task between one's
  own list and a shared one is a copy there with new ids plus a delete here (restorable), since neither server
  takes a move across.
- **Windows** (`sync-worker.ps1`) and **Linux/macOS** (`local/shares.mjs`): the shared list is a normal file in
  `lists/`, so editors and AI assistants keep working on it. `lists/.remotes.json` binds files to their owners'
  servers ([file-format.md](file-format.md#other-files-in-the-data-folder)); the key is in `sync/remotes.json`.
  The engine for one's own server leaves bound files out; each bound file has an engine of its own
  (`Invoke-SyncCycle` / `syncCycle` with a scope: that one file is that project; nothing about the list
  itself is sent; its file comes back if it is removed by hand; the tab order keeps every other list's
  place). The owner renaming the list renames the file, and the binding follows in the same step. A name another
  list has already (at join, or the owner's rename) becomes "Groceries (from nuca)" before it gets a number.
  Every change to `.remotes.json` happens in the sync loop's thread (Windows) or synchronously between engine
  steps (Node), so the engine for one's own server never sees a shared file unbound. Turning one's own sync off
  or on leaves `.remotes.json` and the keys alone: shared lists keep syncing with their owners.
- **View-only files** edited anyway (by hand, an editor, an AI assistant): nothing is sent. Each changed
  field, removed or added line becomes a **notice** (shown with the conflicts: "Not saved", the text that
  was typed, Copy, Dismiss), and the file goes back to the owner's version (lines the owner does not have
  are removed; headings and prose stay). The same happens to a change the owner's server refuses.
- **Joining:** setup registers `saqme://` links on Windows (the registry), Linux (an x-scheme-handler desktop
  entry) and macOS (a small AppleScript applet, `~/Applications/Saqme To Do Invites.app`, that hands the link
  to `saqme invite`). The owner's `/join` page offers: **use it now in this browser** (the owner's own copy of
  the phone app, `/#join=<code>`: nothing to install, no account), **Open in Saqme To Do** (`saqme://join?server=
  …&code=…`, tried by itself in Chromium browsers on computers) and *Copy invite*, and **install Saqme** (the
  one-line installers and the setup guide). The apps always ask before they use up the code. Pasting the link
  works everywhere: Settings > Sync & sharing > *Shared lists*, `saqme join LINK`
  on Linux/macOS. The phone app also
  offers to join when it finds an invite link on the clipboard (where the browser allows reading it: not on
  iPhone, which needs the Paste button there).
- **Move to my Saqme app** (on a list used in the browser): a move code (above) as a link, a QR code on larger
  screens, *Open in Saqme To Do*. The app that opens it takes the list over with no new invite; the browser
  copy then stops syncing and goes ("moved to your Saqme app").
- **Local-only devices** can join: a device without its own sync syncs just its shared lists (the Windows sync
  loop runs whenever there is a shared list; the Linux/macOS app always runs an engine per shared list; the
  phone app, in the browser from the owner's address). Sharing one's *own* lists needs one's own sync.
- **Leave** (instead of Delete, on a shared tab) takes the list off the device: its file goes to
  `lists/.trash`, the binding, key and engine state go, and the key is ended on the owner's server. Nothing
  else changes there. On a paired phone it leaves for all of that person's phones (one key, kept by their
  Worker), not their computers (each has a key of its own).
- **Revoked** (the key gets 401): the list stays as one of the device's own lists, with **new ids** for every
  task (so it never gets mixed up with the owner's copy should it be shared again), synced with the device's
  own server from then on if it has one; the app says so. On Linux/macOS the window's store is told to
  expect the old ids to go (no "deletions paused"). Phones paired with one Worker keep one copy (above).

Covered by `worker/test/node/pwa-shares.test.js` (phone store against in-process Workers: relay, browser,
move, own sync on and off, two owners and one's own list shared out at once), `worker/test/node/local-shares.test.js`
(engine and app, the same combinations) and the shared-list cases in `desktop/tests/sync-core.tests.ps1`. A
checklist for trying it by hand with a second person: [testing-shared-lists.md](testing-shared-lists.md).

## Versions and updates

The apps update themselves and the user's Worker ([setup.md, "Updating"](setup.md#updating)), one device at a
time, so for a while a newer Worker serves older apps, or the other way round. Both must keep syncing.

**API version.** `worker/src/version.js` has the release (`VERSION`, from `worker/package.json`, the one place
it is written) and `API_VERSION`, a whole number that goes up when the Worker learns something apps rely on:

| API | Worker | What came with it |
|---|---|---|
| 1 | before 1.1.0 (it sends no `api`) | sync, pairing codes, reminders |
| 2 | 1.1.0 | shared lists (`/api/shares/*`, `/api/join/*`) |
| 3 | 1.1.0 | the relay for lists shared with a phone that has sync of its own (`/api/remotes/*`) |

Every `/api/health`, `/api/config` and `/api/sync` answer carries `version` and `api` (the local server of the
Linux/macOS app says the same about itself). An answer without `api` comes from a Worker before 1.1.0: API 1.

- **Older Worker, newer app:** the app keeps syncing (nothing in `/api/sync` changed shape). A feature the
  Worker does not have yet says so in plain words instead of failing with an error: "Your sync service runs an
  older version… It is updated together with the app on your computer" (the phone app's `OLDER_SERVER`, the
  Windows app's Share view, `SHARING_API = 2`).
- **Newer Worker, older app:** additions are new fields and new routes only; an app ignores fields it does not
  know. Nothing a Worker answers is ever renamed or removed without an API version that says so.
- **The updater's rule** (`shared/fixtures/update.json`, the same in `local/update.mjs` and
  `desktop/update-core.ps1`): each release's manifest says the oldest Worker API its apps need
  (`minWorkerApi`, from `MIN_WORKER_API`). The Worker is updated first; if that worked (or there is no Worker),
  the apps switch. If it did not (signed out of Cloudflare, an error), the apps still switch when the Worker that
  runs has at least `minWorkerApi` (the Worker is tried again later), and otherwise the whole update waits.
  So sync never runs with apps that need a Worker it does not have.

**The database updates itself.** There is no `wrangler d1 migrations apply` in an update: the Worker carries
its migrations (`worker/src/migrations.js`, the same SQL as `worker/migrations/*.sql`, checked by a test) and
applies what is missing on the first request or cron run after a deploy (`worker/src/schema.js`):

- It reads `meta.schema_version`; when that is current (the usual case) nothing else happens, and the answer is
  kept in memory for the life of the isolate.
- Otherwise it looks at wrangler's own record, the `d1_migrations` table, and applies each migration that is
  not in it as **one batch whose first statement records it there**. Two first requests at the same moment
  both try; the second one's record insert hits the unique name and D1 rolls its whole batch back, so a
  migration runs exactly once. A database that wrangler migrated already (setup before 1.1.0) has those records
  and gets only what is new; one migrated by hand without records is recognised by its tables and columns.
- A migration that fails rolls back completely, and the request answers `503` with `code: "schema"` and the
  reason ("Your sync service could not update its database…"); the next request tries again.

New installs still create the database the same way; the Worker fills it on its first request.

## Guarantees and limits

- A change saved on a device is never dropped by sync: it stays in the outbox until the server has it, and
  the losing side of any concurrent edit is kept as a conflict. Deletes are tombstones.
- Moving a task (drag and drop, Alt+Up/Down, touch drag on the phone) only ever changes its place, never
  deletes it: covered by randomized tests in `desktop/tests/sync-core.tests.ps1` (thousands of moves keep
  every task; moves reach the server as new places only), the widget's self-check (drags through its mouse
  code) and `worker/test/node/pwa-store.test.js`.
- All devices converge to the same lists (covered by `npm run test:e2e`, including randomized concurrent
  edits on two phones and the desktop).
- Field granularity: two edits to different parts of the *same* text are a conflict, not a text merge.
- A desktop file edit is timestamped by the file's save time, so all changes in one save share a timestamp.
- Order within siblings is by fractional keys; a very long run of insertions at the same spot makes keys
  longer (harmless; tested to thousands).
